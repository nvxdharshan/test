Microsoft Authenticator Vulnerability Exposes
One-Time Login Codes to Malicious Apps

Published: 13 March 2026 CVE: CVE-2026-26123 Severity: High (CVSS 7.5) Patch Available: Yes
1. Threat Overview

A vulnerability in Microsoft Authenticator for iOS and Android (CVE-2026-26123) allows a malicious application installed on the same mobile device to intercept one-time login codes (TOTP) and authentication deep links before they are processed by the Authenticator app. If exploited, an attacker gains the ability to complete multi-factor authentication flows as the victim, bypassing MFA protection on any account secured by Microsoft Authenticator without any credential theft, phishing, or network interception.

The vulnerability was disclosed on 12 March 2026. Microsoft has released a patch in the current version of Microsoft Authenticator for both platforms. Organizations must treat this as an urgent update deployment task given the widespread reliance on Authenticator for MFA across Microsoft 365, Azure, and third-party services.

2. Background

Microsoft Authenticator is one of the most widely deployed MFA applications globally, used to generate time-based one-time passwords (TOTP), approve push-based sign-in requests, and handle authentication deep links and QR-based logins for Microsoft and third-party accounts.

A deep link is a specially constructed URI that opens a mobile app and triggers a specific action, such as completing a sign-in flow or approving an authentication request. The vulnerability affects how the Authenticator app registers and exclusively handles these authentication URIs, creating an opportunity for other apps to intercept the link before the Authenticator receives it.

BYOD environments are the highest-risk deployment context for this vulnerability. On BYOD devices, the organization has no direct control over which other apps are installed alongside Authenticator, and employees often grant broad permissions to third-party apps without awareness of the associated risk.

3. Technical Vulnerability Details

The flaw originates in the way Microsoft Authenticator registers URI scheme handlers on iOS and Android. On both platforms, it is possible for a separately installed application to declare itself as a handler for the same authentication URI schemes used by Microsoft Authenticator. When the operating system presents a disambiguation prompt (or silently routes the link based on install order or app permissions), the malicious app can receive the deep link instead of Authenticator.

TOTP Code Interception

Where authentication flows deliver a one-time code via URI, the malicious app receives the code and can use it to complete a sign-in within the TOTP validity window (typically 30 seconds).

Deep Link Hijacking

Sign-in deep links that carry authentication tokens or session parameters are rerouted to the malicious app, which can extract embedded credentials and replay them against the target service.

QR-Based Login Abuse

QR code scanning flows that invoke an authentication URI are similarly vulnerable, allowing the malicious app to intercept the scan result before Microsoft Authenticator processes it.

Exploitation Preconditions

For the attack to succeed, a malicious app must already be installed on the victim’s device, and the user must either trigger an authentication deep link while the malicious app is configured as a handler, or scan a QR code that invokes the vulnerable URI scheme. The attack does not require root access, network positioning, or any interaction beyond the victim performing a routine sign-in.

4. How the Attack Works

An attacker first establishes a presence on the victim’s device via a malicious app, which may be disguised as a productivity tool, utility, or even a legitimate-looking clone of a known app distributed outside official app stores. The malicious app registers itself as a handler for authentication URI schemes used by Microsoft Authenticator.

When the victim initiates a sign-in to a Microsoft or third-party account protected by Authenticator, the OS generates or receives an authentication deep link. If the malicious app has registered for the same scheme, the OS may present a disambiguation dialog or, on some configurations, silently route the link to the most recently installed handler. The user, not expecting a different app to handle an authentication link, may unknowingly select the malicious app or the OS may route it automatically.

The malicious app then receives the one-time code or signed authentication token embedded in the deep link. Using this credential, the attacker completes the MFA challenge from their own device or infrastructure, gaining authenticated access to the victim’s account. The victim receives no warning and the sign-in appears to originate from a known authentication flow.

6. Risk and Impact
Organizational Risk Summary

A successful exploit delivers authenticated account access to an attacker without requiring a password. From the target service perspective, the login is indistinguishable from a legitimate MFA-protected sign-in. The attacker can access email, files, cloud applications, administrative portals, and any other resource the victim account has permissions to reach. In BYOD environments used by staff with elevated M365 or Azure privileges, the potential impact is severe.

Secondary risks include lateral movement via accounts that share the same Authenticator-protected credentials, persistence established through app registrations or OAuth grants made during the attacker’s session, and exfiltration of sensitive data from SharePoint, OneDrive, or Teams before the session is revoked.

7. Indicators of Compromise

The following observable patterns may indicate exploitation of CVE-2026-26123 in your environment. None are individually conclusive but should trigger further investigation when observed together.

Type Indicator Recommended Action
Anomalous Sign-In Successful MFA-protected sign-in from a device or location not associated with the user, with no prior failed attempts Investigate via Azure AD Sign-In Logs; revoke session
URI Handler Conflict User reports an unexpected app appearing as a handler when tapping a sign-in link or scanning a QR code Quarantine device; remove unknown app; audit installed apps
Unusual OAuth Grant New third-party app OAuth consent recorded in Azure AD during or shortly after a sign-in event Revoke consent; review app permissions in Azure AD portal
Unexpected Data Access SharePoint, OneDrive, or Exchange access from a user account at an unusual time or with atypical file patterns Alert SOC; initiate account compromise response playbook
Sideloaded App Mobile device management (MDM) telemetry showing a non-store app installed that requests URI scheme handler permissions Flag device as non-compliant; block corporate access until remediated
8. Detection Guidance

Azure AD / Entra ID Sign-In Logs: Filter for MFA-satisfied sign-in events from devices not registered in your Intune or MDM inventory. Cross-reference against user travel patterns and known working hours. Alert on any sign-in where MFA method is Authenticator but the device ID is absent or unrecognized.

Conditional Access Compliance Signals: Enable device compliance requirements in Conditional Access policies. A device running an unpatched Authenticator version should fail compliance checks once minimum version policies are enforced, blocking access before a successful exploit can translate into an authorized session.

MDM App Inventory: Use Intune or your MDM platform to audit installed apps on managed devices. Flag any app that has registered URI scheme handlers matching Microsoft authentication patterns without being Microsoft Authenticator itself.

Microsoft Sentinel: Deploy the Microsoft 365 Defender connector and create analytics rules for the sign-in anomaly patterns listed in the IOC table above. The “Suspicious MFA success from previously unseen device” rule template covers the primary exploitation scenario.

9. Mitigation Steps
1

Update Microsoft Authenticator immediately on all managed devices via Intune. Issue a self-service update notice to all BYOD users with a deadline and confirmation requirement. The current release contains the patch for CVE-2026-26123.

2

Enforce a minimum app version policy via Conditional Access so any device running a version of Authenticator below the patched release is blocked from accessing corporate resources until updated.

3

Instruct all staff to verify that sign-in deep links and QR code scans are handled exclusively by Microsoft Authenticator, and to immediately report any other app appearing as a handler for authentication links.

4

Review Azure AD sign-in logs for MFA-satisfied logins from unrecognized devices over the past 30 days. Revoke active sessions for any accounts showing anomalous patterns and force re-authentication on patched devices.

5

If BYOD devices cannot be updated immediately, instruct affected users to use alternative MFA methods (push notification only, without deep link flows) until the update is confirmed, and avoid scanning QR codes for sign-in purposes.

6

Deploy or confirm mobile threat defence (MTD) solutions on BYOD devices enrolled for corporate access. MTD tools can detect malicious or anomalous apps that register unauthorized URI scheme handlers before they have the opportunity to intercept authentication flows.

10. Security Best Practices
★
Enforce minimum app version policies in Conditional Access for all authentication apps, not just Microsoft Authenticator. Unpatched MFA clients represent a recurring attack surface as authentication app vulnerabilities become more common targets.
★
Restrict BYOD device access using Intune App Protection Policies that do not require full device enrolment, allowing you to enforce app-level controls (including version requirements) on personal devices without full MDM management.
★
Require managed devices for users with privileged access to M365 Admin Center, Azure portal, and production infrastructure. BYOD devices should not hold privileged account sessions regardless of MFA method.
★
Migrate high-value accounts to phishing-resistant MFA methods (FIDO2 hardware keys or Windows Hello for Business) that are immune to deep link interception and push notification fatigue attacks.
★
Implement a formal mobile device security policy for BYOD that prohibits sideloading of apps from outside official stores, and include mobile device security awareness in annual security training.
★
Enable Microsoft Entra ID Protection risk-based Conditional Access policies that automatically block or challenge sign-ins flagged as high-risk, providing a compensating control when individual vulnerabilities exist in the MFA stack.
★
Subscribe to Microsoft Security Response Center (MSRC) update notifications for Microsoft Authenticator and all other identity-critical apps. Authentication app patches should be treated with the same urgency as OS-level security updates.
